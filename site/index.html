JSON Schema,
built for OO domains.

JSON Schema was designed to validate arbitrary JSON structures — not to model class hierarchies. JSON Object Schema (OOJS) fills that gap: first-class inheritance, abstract types, discriminator dispatch, and typed relationships, with a compiler to JSON Schema 2020-12 for toolchain compatibility.

The Problem

JSON Schema was not designed for OO

JSON Schema is excellent at describing the shape of arbitrary JSON. But modeling a proper OO type hierarchy forces you into workarounds that are verbose, fragile, and non-standard across tools.

🔁

No inheritance keyword

Inheritance requires allOf + $ref. Subtypes must re-declare all ancestor required fields — add one field to a base type and every subtype schema needs a manual update.

🚫

No abstract types

JSON Schema has no concept of a type that cannot be directly instantiated. Simulating it requires if / then / not hacks that validators implement inconsistently.

📐

Polymorphism is O(N)

oneOf forces the validator to try every branch until one matches. For a hierarchy with 30 subtypes, every polymorphic value validates 30 schemas. There is no standard discriminator in core JSON Schema.

🔗

Relationships are untyped

A foreign-key reference to another object is just "type": "string". The target type is lost. No tooling, no code-gen, no navigation — just an opaque string.

Side-by-Side

OO constructs: JSON Schema vs OOJS

The same domain modeled in both languages. OOJS examples are executable against any conforming reference implementation.

01 / Inheritance

Single inheritance with extends

Key difference: In JSON Schema, required in each subtype must include all ancestor fields. Add colour to Vehicle.required and you must update every subtype schema. In OOJS the effective required set is the union across the full ancestor chain — computed automatically by the validator.
02 / Abstract Types

Preventing direct instantiation with "abstract": true

JSON Schema 2020-12
{
  "$defs": {
    "Shape": {
      "type": "object",
      "properties": {
        "shapeType": { "type": "string" },
        "color":     { "type": "string" }
      },
      "required": ["shapeType", "color"],
      "if": {
        "properties": { "shapeType": { "const": "Shape" } },
        "required": ["shapeType"]
      },
      "then": { "not": {} }
    },
    "Circle": {
      "allOf": [
        { "$ref": "#/$defs/Shape" },
        {
          "properties": {
            "radius": { "type": "number", "minimum": 0 }
          },
          "required": ["shapeType", "color", "radius"]
        }
      ]
    }
  }
}
// Non-standard: validator support for this pattern varies.
// There is no spec-defined way to prevent direct instantiation.
JSON Object Schema
{
  "$oojs": "1.0",
  "discriminator": "_type",
  "types": {
    "Shape": {
      "abstract": true,
      "properties": {
        "color": { "type": "string" }
      },
      "required": ["color"]
    },
    "Circle": {
      "extends": "Shape",
      "properties": {
        "radius": { "type": "number", "minimum": 0 }
      },
      "required": ["radius"]
    },
    "Rectangle": {
      "extends": "Shape",
      "properties": {
        "width":  { "type": "number", "minimum": 0 },
        "height": { "type": "number", "minimum": 0 }
      },
      "required": ["width", "height"]
    }
  }
}
// ABSTRACT_TYPE error code returned if _type == "Shape"
Key difference: "abstract": true is part of the OOJS spec — all conforming validators must reject instances with a discriminator value pointing to an abstract type, returning error code ABSTRACT_TYPE. No hacks, no if/then, no cross-validator inconsistency.
03 / Polymorphism & Discriminator Dispatch

Identifying the concrete type at validation time

JSON Schema 2020-12
{
  "properties": {
    "entry": {
      "oneOf": [
        { "$ref": "#/$defs/Observation" },
        { "$ref": "#/$defs/Diagnosis"   },
        { "$ref": "#/$defs/Procedure"   },
        { "$ref": "#/$defs/Referral"    },
        { "$ref": "#/$defs/Prescription"}
      ]
    }
  }
}
// Validator tries Observation schema → fails or passes
// Validator tries Diagnosis schema → fails or passes
// Validator tries Procedure schema → ...
// O(N) cost: every added subtype slows all validations

// OpenAPI 3.x adds "discriminator" as a vendor extension
// but it is not part of core JSON Schema 2020-12.
JSON Object Schema
{
  "$oojs": "1.0",
  "$id": "https://example.org/clinical",
  "discriminator": "_type",
  "types": {
    "ClinicalEntry": {
      "abstract": true,
      "properties": {
        "id":        { "type": "string" },
        "timestamp": { "type": "string", "format": "date-time" },
        "subjectId": { "type": "string" }
      },
      "required": ["id", "timestamp", "subjectId"]
    },
    "Observation":  { "extends": "ClinicalEntry", "properties": { "code": { "type": "string" }, "value": { "type": "number" } }, "required": ["code", "value"] },
    "Diagnosis":    { "extends": "ClinicalEntry", "properties": { "icdCode": { "type": "string" }, "certainty": { "type": "string", "enum": ["confirmed","probable","possible"] } }, "required": ["icdCode","certainty"] },
    "Procedure":    { "extends": "ClinicalEntry", "properties": { "code": { "type": "string" } }, "required": ["code"] },
    "Referral":     { "extends": "ClinicalEntry", "properties": { "targetDept": { "type": "string" } }, "required": ["targetDept"] },
    "Prescription": { "extends": "ClinicalEntry", "properties": { "drug": { "type": "string" }, "dose": { "type": "string" } }, "required": ["drug","dose"] }
  }
}
// Validator reads "_type" once → O(1) map lookup
// N subtypes = same cost as 1 subtype
Key difference: OOJS discriminator dispatch is O(1) — read one field, look up the type in a hash map, validate exactly one schema. JSON Schema's oneOf is O(N) — every branch runs until exactly one passes. For hierarchies with dozens of subtypes (common in healthcare, ERP, game engines), the difference is measurable. OOJS also enforces discriminator value uniqueness across the schema at load time, so the O(1) lookup is always unambiguous.

Key difference: In OOJS, "type": "Motor" is a first-class type reference — the target is a named type in the schema registry. This enables code generators to emit correctly typed fields, documentation tools to show the class hierarchy, and IDE plugins to navigate to the Motor definition. In JSON Schema, $ref is a URI pointer with no type-system meaning; the name is just a path component.
05 / Associations (Typed ID References)

Horizontal relationships with refType

JSON Schema 2020-12
{
  "$defs": {
    "Invoice": {
      "type": "object",
      "properties": {
        "invoiceId": { "type": "string" },
        "amount":    { "type": "number", "minimum": 0 },
        "dueDate":   { "type": "string", "format": "date" },
        "customerId": { "type": "string" }
      },
      "required": ["invoiceId", "amount", "customerId"]
    }
  }
}
// customerId: just a string.
// What does it point to? Customer? User? Account?
// No schema-level answer. Developers must read docs
// or source code to find out.
JSON Object Schema
{
  "$oojs": "1.0",
  "$id": "https://example.org/billing",
  "imports": { "core": "https://example.org/schemas/core" },
  "discriminator": "_type",
  "types": {
    "Invoice": {
      "properties": {
        "invoiceId": { "type": "string" },
        "amount":    { "type": "number", "minimum": 0 },
        "dueDate":   { "type": "string", "format": "date" },
        "customer":  { "refType": "core.Customer" }
      },
      "required": ["invoiceId", "amount", "customer"]
    }
  }
}
// customer: typed ID ref → core.Customer (imported type).
// Value is a plain string ID at runtime — no wire-format change.
// imports: { alias: uri } — types referenced as alias.TypeName
// Docs show: ─── Invoice ──→ core.Customer
Key difference: refType declares the semantic type of an ID reference without embedding the target object. The JSON value is still a string, so there is no wire-format change. But the schema now carries enough information for code generators to emit typed foreign keys, for doc tools to draw relationship diagrams, and for IDE plugins to offer navigation. Cross-schema references work through the imports mechanism.

additionalProperties
Default false = closed world: any property not in the type's effective property set causes an ADDITIONAL_PROPERTY error. Set to true for open-world schemas where extra properties are allowed and silently ignored. Applies at the schema level, not per type.
discriminatorValue
By default the discriminator value equals the type name ("Car" → _type: "Car"). Use discriminatorValue to override this — e.g. for snake_case wire values or versioned names. For imported types the default is "alias.TypeName" (e.g. "core.Customer"), overridable the same way. Values must be unique across the entire registry.
required[] — own properties only
Each type's required array must list only its own properties, not inherited ones. The validator computes the effective required set as the union across the full ancestor chain. Listing an inherited property in a subtype's required causes a schema load error.

Graph Documents

A single JSON file containing multiple independent objects that reference each other by ID — without nesting and without duplication. Cycles are handled safely via two-pass validation.

Schema (OOJS)
{
  "$oojs": "1.0",
  "discriminator": "_type",
  "types": {
    "Person": {
      "properties": {
        "personId": { "type": "string" },
        "name":     { "type": "string" },
        "cars": {
          "type": "array",
          "items": { "type": "Car" }
        }
      },
      "required": ["personId", "name"]
    },
    "Car": {
      "properties": {
        "carId": { "type": "string" },
        "make":  { "type": "string" },
        "owner": { "type": "Person" }
      },
      "required": ["carId", "make", "owner"]
    }
  }
}
Graph Document (instance)
{
  "$oojs": "1.0",
  "roots": [
    {
      "$id":      "person-1",
      "$type":    "Person",
      "personId": "person-1",
      "name":     "Alice",
      "cars":     [{ "$ref-id": "car-1" },
                   { "$ref-id": "car-2" }]
    }
  ],
  "objects": {
    "car-1": {
      "$id":   "car-1",
      "$type": "Car",
      "carId": "car-1",
      "make":  "Toyota",
      "owner": { "$ref-id": "person-1" }

Performance

O(1) discriminator dispatch

Polymorphic validation is the hot path in any OO domain. OOJS and JSON Schema take fundamentally different approaches — with very different scaling characteristics.

JSON Schema — oneOf
O(N)

Every polymorphic value must be validated against all N branch schemas. The validator tries each one sequentially. The first branch that passes wins; if none do, the validation reports all N failures. Adding subtypes directly degrades throughput.

  • 10 subtypes → 10 schema executions per value
  • 50 subtypes → 50 schema executions per value
  • Error messages reference all 50 failing branches
  • No standard way to short-circuit
OOJS — discriminator lookup
O(1)

Validator reads the discriminator field (e.g. _type) from the instance, does a hash-map lookup into the type registry, and validates exactly one schema. Adding subtypes has zero impact on validation cost of any individual value.

  • 10 subtypes → 1 schema execution per value
  • 50 subtypes → 1 schema execution per value
  • Discriminator uniqueness checked at schema load, not per-call
  • Unknown type → immediate UNKNOWN_TYPE error
Real-world impact: In a clinical domain with 40+ entry types, a batch validation of 10,000 records against a JSON Schema oneOf runs roughly 40× more schema evaluations than the same batch against an OOJS schema with discriminator dispatch. This does not mean 40× slower wall-clock time — the actual speedup depends on schema complexity, branch count, and validator implementation. The asymptotic advantage is structural and permanent.

Code Generation

Schemas that describe types, not just shapes

Because OOJS types are named, inheritance is explicit, and relationships carry type information, the schema structure contains enough semantic information to drive code generators — without heuristics or structural inference.

Current status: None of the 7 reference implementations include a code generator. The structural properties below describe what a generator could produce mechanically from any OOJS schema — this is a community opportunity.

A single OOJS schema provides unambiguous source material for generating idiomatic output in any target: named types with declared inheritance, explicit vertical vs horizontal relationships, discriminator metadata, and open/closed-world flags.

  • TypeScript interfaces / classes
    extends maps directly to interface extends. refType emits a typed ID field. Abstract types → no-instantiate comment.
  • Python dataclasses / Pydantic models
    Inheritance chain preserved. refType emits an annotated string field with a forward-reference comment.
  • Java / C# classes
    Abstract types → abstract class. refType → typed ID field with Javadoc/XML doc pointing to the target class.
  • OpenAPI 3.x component schemas
    Level-2 implementations emit JSON Schema 2020-12 output directly. Plug into any OpenAPI toolchain.
  • Database migrations
    Table-per-class hierarchies derivable from the inheritance graph. refType → foreign-key columns.
  • Relationship / ER diagrams
    Vertical vs horizontal, directionality, and owning side are all declared — enough structure to generate ER diagrams automatically.
